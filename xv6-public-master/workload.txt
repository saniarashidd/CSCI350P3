graph1: This graph represents the results of running test1.c, which implements a mixed workload that includes an IO intensive process (PID 4) and a CPU intensive process (PID 3). PID 3 starts briefly in Q0 (Highest) for its initial time slice. Because it continuously consumes its entire time slice without yielding, the MLFQ scheduler demotes it downward through Q1 (Medium) and eventually into Q2 (Lowest), where it spends the majority of its time executing long blocks of continuous CPU service. It is periodically boosted back up to Q0 and this pattern repeats. Because PID 4 almost immediately yields to handle the print statement before its time slice expires. Since PID 4 is almost always waiting/sleeping on I/O rather than actively running instructions on the processor, its actual CPU footprint is minuscule- appearing as just that single thin blue sliver at the very beginning.

graph2: This graph represents the results of running test2.c, which implements a workload that demonstrates how priority boost can improve performance of a long running CPU bound process. The graph displays constant vertical stripes across all three priority tiers (Q0, Q1, and Q2), showing how 10 processes work their way down priority queues before being boosted up and repeating.

graph3: This graph represents the results of running test3.c, which implements a workload that demonstrates how MFQ scheduler can be gamed. Process 3 manages to stay in the highest priority queue by yielding the CPU before its time slice expires.
